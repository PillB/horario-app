# Supabase schema setup

This guide explains how to create the Supabase tables that support the scheduling and demand-forecasting flows used by the app. The SQL below can be run in the Supabase SQL editor, via the Supabase CLI, or as part of a migration file for local development and CI.

## Required tables

The schema uses three tables. Each table includes an auto-generated primary key for traceability while exposing the fields used by the app.

### `shifts`
- `date` (`date`, required)
- `role` (`text`, required)
- `worker_id` (`text`, required)
- `hours` (`numeric(5,2)`, required, must be >= 0)
- `id` (`bigint`, primary key, generated identity)

Recommended index: `(date, role)` to speed up role-level shift lookups.

### `external_signals`
- `date` (`date`, required)
- `role` (`text`, required)
- `signal_type` (`text`, required)
- `weight` (`numeric(10,4)`, required)
- `id` (`bigint`, primary key, generated identity)

Recommended index: `(date, role, signal_type)` for quickly fetching signals for a specific day and role.

### `demand_targets`
- `date` (`date`, required)
- `role` (`text`, required)
- `required` (`numeric(10,2)`, required)
- `notes` (`text`, optional)
- `confidence` (`numeric(5,4)`, optional)
- `lower_bound` (`numeric(10,2)`, optional)
- `upper_bound` (`numeric(10,2)`, optional)
- `source` (`text`, optional)
- `id` (`bigint`, primary key, generated identity)

Primary key: `id`.

Unique constraint: `(date, role)` to support `onConflict` upserts from the app.

Recommended index: `(date, role)` (created implicitly by the unique constraint).

### `onboarding_progress`
- `account_id` (`text`, required)
- `user_id` (`text`, optional) — set to `null` to store account-level progress shared by multiple users
- `workers_completed` (`boolean`, required, defaults to `false`)
- `templates_completed` (`boolean`, required, defaults to `false`)
- `forecast_completed` (`boolean`, required, defaults to `false`)
- `id` (`bigint`, primary key, generated identity)

Primary key: `id`.

Unique constraint: `(account_id, user_id)` to support `onConflict: ['account_id', 'user_id']` upserts from the app.

## Provisioning SQL

Use this SQL to create the tables, indexes, and unique constraint. You can paste it into the Supabase SQL editor or save it as a migration (for example, `supabase/migrations/20240101000000_init.sql`).

```sql
-- shifts
create table if not exists public.shifts (
  id bigint generated by default as identity primary key,
  date date not null,
  role text not null,
  worker_id text not null,
  hours numeric(5,2) not null check (hours >= 0)
);

create index if not exists shifts_date_role_idx on public.shifts (date, role);

-- external_signals
create table if not exists public.external_signals (
  id bigint generated by default as identity primary key,
  date date not null,
  role text not null,
  signal_type text not null,
  weight numeric(10,4) not null
);

create index if not exists external_signals_date_role_type_idx on public.external_signals (date, role, signal_type);

-- demand_targets
create table if not exists public.demand_targets (
  id bigint generated by default as identity primary key,
  date date not null,
  role text not null,
  required numeric(10,2) not null,
  notes text,
  confidence numeric(5,4),
  lower_bound numeric(10,2),
  upper_bound numeric(10,2),
  source text
);

alter table public.demand_targets
  add constraint demand_targets_date_role_key unique (date, role);

-- onboarding_progress
create table if not exists public.onboarding_progress (
  id bigint generated by default as identity primary key,
  account_id text not null,
  user_id text,
  workers_completed boolean not null default false,
  templates_completed boolean not null default false,
  forecast_completed boolean not null default false
);

alter table public.onboarding_progress
  add constraint onboarding_progress_account_user_key unique (account_id, user_id);
```

## RLS policies

Enable Row Level Security (RLS) on each table and add policies to enforce read/write scopes. The `auth.role()` helper matches the API key role that calls the Supabase REST endpoint.

```sql
-- Enable RLS
alter table public.shifts enable row level security;
alter table public.external_signals enable row level security;
alter table public.demand_targets enable row level security;
alter table public.onboarding_progress enable row level security;

-- Read access for anon key (client-side reads)
create policy if not exists "Anon read shifts" on public.shifts
  for select using (auth.role() = 'anon');

create policy if not exists "Anon read external signals" on public.external_signals
  for select using (auth.role() = 'anon');

create policy if not exists "Anon read demand targets" on public.demand_targets
  for select using (auth.role() = 'anon');

create policy if not exists "Anon read onboarding progress" on public.onboarding_progress
  for select using (auth.role() = 'anon');

-- Write access reserved for service role (server-side upserts)
create policy if not exists "Service role writes shifts" on public.shifts
  for all
  using (auth.role() = 'service_role')
  with check (auth.role() = 'service_role');

create policy if not exists "Service role writes external signals" on public.external_signals
  for all
  using (auth.role() = 'service_role')
  with check (auth.role() = 'service_role');

create policy if not exists "Service role writes demand targets" on public.demand_targets
  for all
  using (auth.role() = 'service_role')
  with check (auth.role() = 'service_role');

-- Allow anon upserts for onboarding flags while keeping deletes restricted to the service role
create policy if not exists "Anon upsert onboarding progress" on public.onboarding_progress
  for insert
  with check (auth.role() = 'anon');

create policy if not exists "Anon update onboarding progress" on public.onboarding_progress
  for update
  using (auth.role() = 'anon')
  with check (auth.role() = 'anon');

create policy if not exists "Service role manages onboarding progress" on public.onboarding_progress
  for all
  using (auth.role() = 'service_role')
  with check (auth.role() = 'service_role');
```

- Anonymous reads allow the Expo client to fetch planning data with the public key.
- Service role keys should only be used by trusted backends or CI jobs to insert, update, or delete records.

## Applying the migration locally and in CI

1. **Local development**
   - Link your local Supabase CLI project (`supabase link --project-ref <ref>`).
   - Save the SQL above as `supabase/migrations/<timestamp>_init.sql`.
   - Apply it locally with `supabase db push`.

2. **CI**
   - Add the migration file to version control.
   - In CI, run `supabase db push --db-url "$SUPABASE_DB_URL"` or use the Supabase SQL API to execute the same SQL so your ephemeral databases match production.

3. **Dashboard quick start**
   - If you prefer the UI, paste the SQL blocks into the Supabase Dashboard SQL editor and run them once per environment.

With the tables, indexes, unique constraint, and RLS policies in place, the app can upsert `demand_targets` records with `onConflict: ['date', 'role']` and read data securely using the appropriate Supabase keys.
